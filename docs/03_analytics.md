# 3. Аналитика и метрики

Все расчёты выполняются в SQL (витрины `sql/marts.sql`, инструменты `src/agent/tools.py`) и Python (`src/fair_price.py`). Языковая модель в расчётах не участвует. Методы — статистические и rule-based: медиана, межквартильный размах (IQR), MAD, робастный z-показатель. Они устойчивы к выбросам, которых в закупочных данных много, и каждый вывод можно объяснить человеку.

Общие правила для всех методов:

- **Сопоставимость.** Цены сравниваются только внутри группы «код ЕНСТРУ + базовая единица измерения». Цена и количество предварительно приведены к базовой единице (граммы → килограммы и т. п.).
- **Эталонные позиции.** В расчёт эталонов входят только позиции с корректной ценой, количеством и суммой из действующих договоров (`is_benchmark`, см. «Схема хранения», 2.3).
- **Минимальная выборка.** Статистика по группе меньше 5 позиций не строится: агент прямо отвечает «недостаточно данных».

## 3.1. Отклонение цены от средневзвешенной (аномалии)

Обязательный класс ТЗ: «Найди закупки с отклонением цены > 30% от средневзвешенной по данному ЕНСТРУ».

Для каждой позиции *i* в группе *G* («ЕНСТРУ + единица») средневзвешенная цена считается **по остальным позициям группы**, без самой позиции:

```
            Σ (pⱼ · qⱼ),  j ∈ G, j ≠ i
ref_i  =  ───────────────────────────────
               Σ qⱼ,      j ∈ G, j ≠ i

deviation_i = p_i / ref_i − 1
```

где *p* — цена за базовую единицу, *q* — количество в базовых единицах. Исключение самой позиции (leave-one-out) не даёт крупной закупке «утянуть» эталон к своей цене и скрыть собственное завышение.

**Аномалия:** `|deviation| > 30%` в группе от 5 позиций. Порог и направление («завышенные» → только вверх) берутся из вопроса.

**Подтверждение.** Средневзвешенная цена чувствительна к разнородным товарам под одним кодом ЕНСТРУ, поэтому каждая найденная аномалия дополнительно проверяется справедливой ценой (3.2). В ответе агент разделяет найденные отклонения на:

- подтверждённые (справедливая цена тоже показывает завышение или занижение);
- вероятные ошибки данных (цена отличается от справедливой в 10 раз и больше);
- не проверенные (не хватило аналогов для справедливой цены).

В примерах сначала идут подтверждённые аномалии с высокой и средней уверенностью, затем остальные, внутри группы — по сумме переплаты.

## 3.2. Справедливая цена (Fair Price)

Обязательный класс ТЗ: «Оцени адекватность цены лота относительно аналогичных контрактов других ведомств в идентичном городе поставки». ТЗ требует учесть сравнительный подход, региональный коэффициент, инфляцию и сезонность.

### Определение

**Справедливая цена позиции** — медиана цен аналогичных закупок, приведённых к условиям этой позиции (месяц, сезон, регион):

- **аналогичные** — тот же код ЕНСТРУ и базовая единица;
- **других ведомств** — заказчик другой (свои закупки не используются как эталон для самих себя);
- **за сопоставимый период** — дата договора в окне ±12 месяцев;
- **в том же городе** — если там не меньше 5 аналогов; иначе в той же области; иначе по всей стране.

### Расчёт по шагам

1. **Инфляция.** Месячная инфляция (месяц к месяцу) из `data/reference/cpi_kz.csv` накапливается в индекс цен *I(t)*. Все цены переводятся в сопоставимые: `real = p / I(t)`. Для месяцев после последнего в файле используется последнее значение индекса.
2. **Сезонность.** Для каждого месяца года считается типичное отклонение цен от медианы своей группы (в логарифмах). Эффект «сжимается» к нулю при малом числе наблюдений и центрируется так, чтобы среднее по месяцам было 1:

   ```
   season(m) = exp( median(log(real / median_группы)) · n_m / (n_m + 100) )
   ```
3. **Региональный коэффициент.** Так же, после снятия сезонности, считается типичное отклонение цен в каждом городе. Коэффициент строится только для городов, где не меньше 30 позиций, со сжатием `n / (n + 50)`:

   ```
   region_k(город) = exp( median(log ratio) · n / (n + 50) )
   ```
4. **Аналоги и медиана.**
   - если аналоги из того же города — региональная поправка не нужна: берётся медиана цен `real / season`, затем умножается на `I(t) · season(m)` этой позиции;
   - если из области или страны — цены аналогов дополнительно делятся на свой `region_k`, а медиана умножается на `region_k` города позиции.

   Тем же способом считаются Q1 и Q3 аналогов.
5. **Вердикт.**

   | Вердикт | Условие |
   |---|---|
   | вероятная ошибка данных | цена ≥ 10 × справедливой или ≤ справедливой / 10 |
   | завышена | цена > справедливой на 30% **и** цена > Q3 + 1,5 · IQR аналогов |
   | занижена | цена < справедливой на 30% **и** цена < Q1 − 1,5 · IQR аналогов |
   | в норме | остальные случаи |
   | недостаточно данных | меньше 5 аналогов даже по стране |

   Двойное условие (30% и выход за границу выброса) защищает от ложных срабатываний в группах с естественно большим разбросом цен.
6. **Переплата:** `(цена − справедливая) × количество` — показывается в ответе как оценка суммы завышения.

### Уверенность оценки

Разброс аналогов: `dispersion = IQR / 1,349 / медиана` (IQR / 1,349 — оценка стандартного отклонения, устойчивая к выбросам).

| Уверенность | Условие |
|---|---|
| высокая | ≥ 20 аналогов и dispersion ≤ 0,35 |
| средняя | ≥ 8 аналогов и dispersion ≤ 0,8 |
| низкая | остальные случаи |

Если аналоги нашлись только по стране, уверенность снижается на один уровень. Для лота из нескольких позиций итоговая уверенность — минимальная по позициям.

### Что получилось на данных

| Показатель | Значение |
|---|---|
| Позиций в эталоне | 70 598 |
| Оценено справедливой ценой | 33 309 (47%): по городу 20 961, по области 4, по стране 12 344 |
| Недостаточно аналогов | 37 289 (53%) |
| Завышены / занижены / в норме / вероятные ошибки | 3 730 / 686 / 25 802 / 3 091 |
| Сезонная поправка | 1,00 для всех месяцев |
| Региональных коэффициентов | 4, от 0,99 до 1,00 |

Сезонность и региональные коэффициенты реализованы, но на этих данных их эффект близок к нулю: после сжатия к нулю оставшиеся поправки меньше 1%. Это ожидаемо для 27 организаций, большинство которых закупает в одних и тех же городах. На более широкой выборке те же формулы дадут заметные поправки без изменения кода.

## 3.3. Нетипичный рост объёмов

Обязательный класс ТЗ: «Выяви нетипичное завышение количества ТРУ по сравнению с предыдущими годами».

**Единица анализа** — тройка «организация + код ЕНСТРУ + базовая единица» за год. Количество берётся из годового плана (`plan.count`, только активные и неудалённые пункты), приведённое к базовой единице.

```
baseline     = среднее плановое количество за все предыдущие годы (с 2024)
ratio        = plan_qty / baseline
log_ratio    = ln(ratio)
robust_z     = 0,6745 · (log_ratio − медиана log_ratio за год) / MAD за год
```

MAD — медиана абсолютных отклонений от медианы. Он считается по всем позициям года, поэтому «нетипичность» определяется относительно общего фона: если в год все закупки выросли вдвое, отдельный рост ×2 нетипичным не считается.

| Вердикт | Условие |
|---|---|
| статистически значимый рост | ratio ≥ 1,5 **и** robust_z ≥ 3,5 |
| повышенный объём | ratio ≥ 1,5 |
| в норме | ratio < 1,5 |
| нет истории | товар не закупался в прошлые годы |

Порог 3,5 — стандартная граница выброса для робастного z-показателя (Iglewicz & Hoaglin). Порог роста ×1,5 можно задать в вопросе («в 2 раза»).

**Стоимость прироста:** `(plan_qty − baseline) × plan_amount / plan_qty` — сколько стоит «лишнее» количество по плановой цене. В примерах ответа сначала идут статистически значимые случаи, затем по стоимости прироста.

## 3.4. Сравнение цен и суммы расходов

**Сравнение цен (`compare_prices`):** по группе «ЕНСТРУ + единица» — N, средневзвешенная цена `Σ(p·q) / Σq`, медиана, Q1, Q3, min, max, разрез по заказчикам, поставщикам, городам или годам; минимальные и максимальные цены со ссылками на договоры. Если средневзвешенная и медиана различаются больше чем в 1,5 раза, агент предупреждает о выбросах и советует ориентироваться на медиану.

**Суммы (`spend_summary`):** сумма по последней версии каждого договора. Расторгнутые и заменённые версии не учитываются, если не запрошено иначе. При фильтре по товару или ЕНСТРУ суммируются только подходящие позиции договоров. Разбивка — по поставщикам, заказчикам, ЕНСТРУ, годам или месяцам. Если в вопросе одна организация, разбивка идёт по её контрагентам.

## 3.7. Метрика точности и методика оценки

Требование ТЗ: точность извлечения фактов (цифр, дат, БИН) не менее 85%.

**Методика (`src/evaluate.py`):**

1. **Набор вопросов.** 30 типовых вопросов (21 на русском, 9 на казахском) покрывают все шесть инструментов, три обязательных класса ТЗ и отказы на вопросы не по теме. Вопросы строятся по реальным БИН, кодам ЕНСТРУ, лотам и договорам из базы и сохраняются в `eval/questions.json`, поэтому набор одинаков от запуска к запуску. Ещё 10 вопросов в свободной форме (`eval/questions_free.json`): синонимы, «прошлый год», «былтыр», опечатки.
2. **Эталон.** Для каждого вопроса эталонные факты считаются **отдельными SQL-запросами**, которые не вызывают код агента: суммы, число договоров, медианы, число отклонений, вердикты, БИН, коды, номера лотов.
3. **Проверка.** Числа ищутся только в «Кратком выводе», чтобы случайное совпадение с датой или номером в примерах не засчитывалось. Денежные суммы допускают округление (до целых тенге от 1 000, иначе до копеек). Идентификаторы ищутся во всём ответе. Если агент выбрал не тот инструмент, все факты вопроса считаются неверными. Для вопросов не по теме проверяется сам отказ.
4. **Метрика:** доля верных фактов от всех эталонных фактов.

**Результаты** (данные на 18.10.2026, отчёт — `eval/report.md`):

| Набор | С моделью (gpt-6.1-sol) | Без модели (правила) |
|---|---|---|
| Типовые вопросы, 101 факт | **99,0%** | **100%** |
| Свободные формулировки, 40 фактов | **97,5%** | 45,0% |
| Верный выбор инструмента | 40 / 40 | 35 / 40 |

Оба промаха с моделью (по одному в каждом наборе) — вопросы о росте объёмов: модель иногда сама ставит порог роста ×2 вместо стандартного ×1,5, и число найденных позиций отличается от эталона (подробнее — в «Рисках и ограничениях»).

**Что метрика проверяет и чего не проверяет.** Для поиска, сумм и сравнения цен эталон — независимый расчёт по исходным данным. Для аномалий, справедливой цены и роста объёмов эталон читает те же витрины, что и агент. Поэтому оценка проверяет, что агент правильно понял вопрос, выбрал метод и без искажений передал результат, но не проверяет правильность самой методики: её обоснование изложено в разделах 3.1–3.3.
